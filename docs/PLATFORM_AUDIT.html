Section 01

Executive Summary

This platform is an in-house test automation system for iOS mobile applications. It was built to test a connected suite of restaurant apps — a consumer-facing booking and ordering app, and a business-facing app used by waiting staff and kitchen staff.

Its central purpose is to take test procedures that a QA engineer would otherwise perform by hand on a phone — open the app, pick a restaurant, book a table, pre-order food, hand the order to the kitchen, confirm the kitchen sees it — and run them unattended against iOS simulators, on demand or when developers push code.

Why it exists

The applications under test span two separate apps used by three different roles. A single business transaction — a diner books a table and pre-orders a meal — passes from the consumer app to the waiter's screen to the kitchen's screen. Testing that by hand means one person juggling two devices and three logins, repeatedly, for every release. That is the specific pain this platform was built to remove.

Who uses it

  • QA engineers — author test scenarios in plain English, run them, read the results.
  • Developers — get a test verdict on a pull request before merging.
  • QA leads — see run history, pass/fail trends, and which tests are queued or running.

What it is designed to test

iOS applications built with React Native. All nine projects registered in the platform database are iOS. Verified via SELECT platform, COUNT(*) FROM test_projects → [('ios', 9)].

The value proposition, stated conservatively

A repeatable cross-app journey that takes a person several minutes of careful two-device operation runs unattended and produces a screenshot-backed report. The platform's own history shows 181 test runs executed to date. That is real, delivered automation — not a projection.

Set expectations here

This is a working internal tool, not a finished commercial product. It runs on one Mac, against simulators, with a single user account. Sections 17 and 19 are the honest counterweight to this summary and should be read alongside it.

Section 02

The Problems It Actually Solves

Only problems with a traced implementation are listed. Problems the platform does not address are absent by design.

1 — Repetitive cross-app regression testing

Traditionally: a tester operates a phone and a tablet simultaneously, logging in and out of three roles, to confirm one booking reaches the kitchen.

Here: the journey is defined once as an ordered set of role segments and replayed on command.

Evidence automation/scenarios/cross_app_flows.py — segment definitions and _run_segment(), which drives consumer → waiter → kitchen across two simulators.

2 — Writing Appium code for every test

Traditionally: each test case becomes Python, with hand-picked selectors that break on redesign.

Here: tests are written as English step lists — click bookAppoitment, select the 2nd time slot, verify Confirmed — and a resolver turns each step into Appium calls at runtime.

Evidence automation/intelligence/scenario_runner.py — run_one() plus a layered resolution strategy over ACCESSIBILITY_ID, IOS_PREDICATE and container-scoped XPATH.

3 — Appium and simulator setup overhead

Traditionally: every engineer maintains their own Appium install, ports, and simulator state.

Here: the platform starts an Appium server per run on a dynamically allocated port and manages simulator boot itself.

Evidence automation/projects/builder.py — ensure_ios_booted(); per-run Appium lifecycle in the appium service layer.

4 — "Which build is even on this simulator?"

Traditionally: nobody is certain whether the device under test has the code being discussed.

Here: the platform pulls, builds once, installs on every selected simulator, then reads the version back off the device and flags a mismatch.

Evidence automation/api/v1/routers/builds.py:194-217 — installed_version() before and after install, with a version_matches flag comparing the artifact's version against what the device reports.

5 — Testing a pull request before merge

Traditionally: a reviewer reads a diff and hopes.

Here: a PR branch is checked out, built, installed and tested, with the verdict posted back to GitHub.

Evidence automation/api/v1/routers/pull_requests.py; automation/integrations/pr_comment.py. Conditional — write-back fires only on webhook-triggered runs. See Section 10.

6 — No shared record of what was tested

Traditionally: results live in one person's terminal.

Here: every run persists to a database with per-step results, screenshots and duration, and renders as an HTML report.

Evidence test_runs and scenario_results tables; automation/api/v1/routers/reports.py — rich_report(). 181 runs recorded: 55 passed, 106 failed, 19 cancelled, 1 stopped.

7 — Getting a fresh build onto every device

Traditionally: install manually, per device, per app.

Here: a dashboard notification reports which projects have unpulled commits; one action pulls, builds once and fans the same artifact out to every selected simulator.

Evidence automation/api/v1/routers/builds.py — GET /builds/updates, POST /builds/deploy; UI in BuildUpdateBell.tsx.
Section 03

Platform Purpose — and Its Boundaries

The platform is a self-hosted execution and reporting system for iOS UI test scenarios, specialised for testing business journeys that cross between a consumer app and a staff app. It handles source checkout, app build, simulator preparation, installation, execution of English-language test steps through Appium, and the collection of results into a shared database and report.

Stated in detail

Three things distinguish it from a generic Appium test suite:

  1. Scenarios are data, not code. A test is rows in the saved_scenarios table — a title, a project, an ordered step list — editable in the browser. 34 exist today.
  2. Cross-app journeys are first-class. A flow is a sequence of role segments, each with its own app, device and login, so one test spans the whole business transaction.
  3. It owns the environment. Repository, build, install, simulator boot and Appium lifecycle are all inside the platform, so a run starts from a known state.

What it is not intended to do

  • Not a device farm. It drives local iOS simulators on the machine it runs on. No physical-device path exists.
  • Not a load or performance testing tool. It records per-run metrics but generates no load.
  • Not a unit or API test runner. It drives applications through their user interface.
  • Not a hosted service. No container definition, no multi-tenancy, one user account in the database.
  • Not an autonomous testing agent. It executes scenarios people wrote. See Section 16 (AI).

Section 05

How Automation Works, End to End

This is the actual path taken when a test runs through the agent, traced through the code.

  1. A run is requested routers/scenarios.py · routers/pull_requests.py · routers/webhooks.py A person presses Run, or GitHub delivers a webhook. Either way a test_runs row is created with job_state = "queued", carrying the project, the branch, the target device and — for PR tests — the PR number. Input: project + scenario/branch. Output: a queued job row. On failure the request returns an HTTP error; nothing is queued.
  2. An agent claims the job agent/main.py polling loop → POST /jobs/poll The agent polls on a loop, authenticating with its shared token. The claim is atomic in the endpoint, so two agents cannot take the same job. Output: a job payload — repo URL, branch, device id, scenario list. On failure the poll returns empty and the agent sleeps and retries. A crashed agent leaves the job queued for another.
  3. Source is fetched and put on the right commit projects/repository.py — clone / checkout_branch / pull Clone if absent, otherwise rebase-pull with autostash. checkout_branch() resets the worktree first so a previous run's artifacts cannot leak in. Output: a working tree at the requested branch. On failure a failed rebase is aborted and the working tree left intact; the job is reported failed rather than force-reset. Local staging patches survive.
  4. The app is built projects/builder.py — build() xcodebuild produces a simulator .app. Existing artifacts are reused unless a rebuild is forced. Output: artifact path, bundle id, version and build number. On failure BuildResult(ok=False, error=…) ends the job; the error text is reported.
  5. The simulator is prepared builder.py — ensure_ios_booted() · agent/main.py — _wipe_app() The target simulator is booted if shut down. When FRESH_INSTALL_PER_JOB is set — used for PR tests — the app is uninstalled first, so the PR build is tested rather than a leftover. On failure the boot message is captured and the device is skipped.
  6. The app is installed and the version confirmed builder.py — install() then installed_version() After installing, the version is read back from the device. If it differs from the artifact's version the install did not take, however green the step looked. On failure the install is recorded ok: false with the reason.
  7. A session is opened Appium server on a per-run port → XCUITest driver An Appium instance is started for this run on its own port, and a driver session is created against the simulator UDID and bundle id. On failure session creation raises; the job is marked failed.
  8. Steps are resolved and performed intelligence/scenario_runner.py — run_one() Each English step is matched to an intent (tap, type, select, scroll, verify, capture) and a target. The target is resolved through layered strategies — accessibility id first, then predicate matching, then container-scoped search. Obstacles that no step asked for — permission prompts, LogBox overlays, system alerts — are cleared by clear_blockers(), which verifies the screen actually changed before claiming success. On failure the step is recorded failed and the remaining steps in that segment are abandoned — later steps would act on the wrong screen and manufacture a false verdict.
  9. Cross-app segments hand over scenarios/cross_app_flows.py — _run_segment() For a cross-app flow, execution moves to the next role — a different app, device and login — carrying the identifier created upstream (a reservation, an order) so the next role verifies the same transaction. On failure the segment aborts. A downstream role cannot report success on a booking that was never made.
  10. Results are reported back agent/main.py — report_status() → POST /jobs/{id}/status Status, logs and a detail string are posted to the platform. A run with zero executed tests reports no_tests rather than passing — pytest exits 0 on an empty suite, which previously produced green runs that tested nothing. On failure a network error loses the update; the job can be left in running until the next backend restart reaps it.
  11. The platform finalises the run runner/service.py — append_agent_logs → _persist_final_status Terminal status, duration and error message are written to test_runs. RCA and visual-regression checks are triggered, and — for webhook-originated runs only — a verdict comment and commit status are posted to GitHub. On failure finalisation depends on the run being present in the service's in-memory active_runs map. If the backend restarted mid-run, the update is dropped. See Section 13.
  12. Results become readable routers/reports.py — rich_report() · dashboard RunDetails The run renders as an HTML report: each step, its verdict, its screenshot, and the failure detail where there is one.

How the parts talk

  • Dashboard → API — REST over HTTP with a bearer token. The base URL derives from window.location.hostname, so colleagues on the LAN reach the same backend.
  • Agent → API — HTTP polling with a shared agent token. The agent pulls work; the platform never pushes to it. This is why an agent can sit behind a firewall.

Architectural note

Section 08

Working With the Platform

Starting it

Two processes. The backend is supervised; the agent runs separately.

./start-backend.sh — or scripts/supervise_backend.sh
.venv/bin/python -m automation.agent.main

Console scripts in .venv/bin/ carry stale shebangs since the project moved; invoke through python -m.

Connecting an application

Register a project with its Git URL and default branch; the platform clones it. Nine projects are registered. routers/projects.py → clone_repository

Choosing a device

Simulators are enumerated live, booted or not, and chosen per action — a PR test targets one device, a build deploy targets several. Nothing is hardcoded; add a simulator and the next action sees it. device_manager/service.py

Creating a test

Three routes, all supported:

  • Type the steps. Plain English, one per line, in the scenario editor.
  • Record them. Open the recorder, tap the live simulator frame, and each tap becomes a step keyed to the real element under your finger.
  • Compose a cross-app flow. Chain role segments into one journey.

Running

Press Run. The run is queued, an agent claims it, and the Job Queue page shows it move from queued to running to a verdict.

When it fails

The step that failed is named, with the reason and the screenshot at the moment of failure. Remaining steps in that segment are skipped rather than run against the wrong screen. There is no automatic retry — you read the report and act.

Reading results

The rich HTML report gives the step-by-step narrative with screenshots. Trends give pass/fail over time. reports.py

The deliberate guard against guessing

Multi-word targets must be fully covered by a candidate before it is accepted. A step reading click book now will not resolve to an element called preOrderBooking — the resolver records the ambiguity and fails the step instead.

Evidence scenario_runner.py — multi-word coverage requirement across resolution strategies, with _last_ambiguous carrying the explanation into the report.

This is a considered trade: more failed steps, fewer false passes. A test that silently books the wrong thing and reports green is worse than one that stops and says it could not find the button.

When an element has no accessibility id

The platform tries visible-text matching and container-scoped search. Where neither works — an unlabelled icon, a custom-drawn control, a canvas — it cannot reliably find the element, and developer instrumentation is required. The application team adds a testID; there is no platform-side workaround.

Distinguish clearly

Platform does today: id, text, container and positional resolution, with an idb fallback for trees Appium under-reports.

Application developers must do: add testID to controls that expose neither a stable id nor stable text.

Proposed only, not built: vision or OCR element location. No such code exists.

Important asymmetry

A PR tested from the dashboard stamps triggered_by = "pr_test:owner/repo#N". The write-back guard requires the prefix github_webhook:. So manually triggered PR tests produce results in the platform but post nothing to GitHub. Only webhook-triggered runs comment back. This is a one-line condition, not a design limit — but today it is the behaviour.

Permissions and tokens

  • GITHUB_TOKEN — needs repo read for clone and PR listing; write on issues and statuses to comment and set commit status.
  • GITHUB_WEBHOOK_SECRET — now mandatory in production. With APP_ENV set to production and no secret configured, the webhook endpoint returns 503 rather than accepting unverified deliveries.
  • GITHUB_REPO_OWNER — default owner for API calls.

The recurring theme

Most defects fixed in this platform were the same class: a step announcing success without verifying it achieved anything. A tap was sent, so the step passed — even though the modal never closed, the checkbox never ticked, the login landed on the wrong role. The countermeasure now built in throughout is verify-after-act: check the screen changed, read the version back off the device, confirm the role, abort the segment rather than continue against the wrong screen.

The log-redaction bug found in revision 2 is the same shape at the infrastructure level: a filter was installed, the code looked protected, and no one checked that it caught anything. It did not.

Section 12

Cross-Application Testing

Implemented — and it is the platform's most distinctive capability. Eleven flows are defined.

The journey

Consumer app: browse, book a table, pre-order. → Business app as waiter: open the reservation, assign a table, take the order. → Business app as kitchen: see the order, mark it ready. Each role is a segment with its own app, device and credentials.

How state carries across

  • Shared backend. The apps talk to the same server, so a booking made by the consumer is genuinely visible to staff. The platform verifies real propagation, not a mock.
  • Identifier hand-off. The reservation or order created upstream is opened by name downstream — _open_reservation and @open_order filter on the expected status (reserved, confirmationpending, inprogress), so a downstream role cannot pick up an unrelated record and report success.
  • Two simulators. Consumer runs on a phone, business on a tablet, each with its own Appium session.

What synchronisation verification actually is

It is an existence-and-status check: the downstream role must find the specific record in the expected state. If the booking never propagated, the segment fails. What is not verified is field-level fidelity — that guest count, notes and timing arrived intact — unless a scenario adds explicit assertions for them.

What remains manual

  • Test-data state — an existing reservation in the right status is often a precondition, not something the flow creates.
  • Interpreting a failed segment: platform bug, app bug, or stale data.
  • Payment settlement beyond order status.

Two gaps worth naming

Orphan recovery is startup-only and partial. _reap_orphaned_runs() marks stuck running rows as failed when the backend starts — but only for the two cross-app bot types, and only at startup. Section 15

Business Value

Each benefit below follows from a capability verified above. No percentage claims are made — the platform holds no before/after measurement of manual effort, so any figure would be invented.

Cross-app journeys become repeatable

The highest-effort manual test — one transaction across two apps and three roles — is defined once and replayed. This is where the labour saving is concentrated, because it is the test people most dislike running by hand.

Test authoring opens beyond programmers

Scenarios are English steps stored as data and edited in a browser. A QA engineer who does not write Python can author, edit and run tests. 34 scenarios exist without anyone maintaining a Python file per test.

Code changes get a verdict before merge

A PR branch is built, cleanly installed and tested on a simulator. Where the trigger is a webhook, the verdict lands on the PR itself.

Results are shared, not personal

181 runs with screenshots and per-step detail are in one queryable place. A failure conversation starts from the same evidence rather than from someone's recollection.

Build provenance is certain

The version installed is read back from the device and compared against what was built. "Are we testing the right build?" becomes a fact rather than an assumption.

Consistency, and honest verdicts

Automated steps do not vary with fatigue. More importantly, the platform is engineered to fail loudly rather than pass optimistically — an unresolvable step stops the segment instead of guessing. A green run means more here than in a system tuned to look green.

Where value is not yet realised

Regression coverage is still narrow — 34 scenarios, and by the team's own tracking only a fraction of the intended consumer catalogue is written, with fewer proven against the app. The execution machinery outpaces the scenario library. The next unit of value comes from writing scenarios, not from building features.

Section 16

Client Questions, Answered From the Code

General

What is this platform?

A self-hosted system that runs iOS app tests automatically on simulators and records the results. It handles source checkout, build, install, execution and reporting.

What problem does it solve?

Chiefly, the manual effort of testing a business journey that crosses two apps and three staff roles — plus the setup burden of Appium and simulator management.

Who will use it?

QA engineers author and run tests; developers get PR verdicts; leads read run history. Today there is one user account in the database.

What applications can it test?

iOS applications, React Native in practice. Nine projects registered, all iOS.

Automation

Can it test complete end-to-end workflows?

Yes — including workflows spanning two apps and three roles. Eleven cross-app flows are defined.

Can it test Android?

Not today. adb device discovery and a Gradle APK build exist in code, but no Android project is registered and no Android run has occurred. Treat Android as unproven work, not a feature.

Can it use real physical devices?

No. Simulators only. No real-device tooling is present anywhere in the codebase.

How does it identify UI elements?

Accessibility id first, then visible-text predicate matching, then container-scoped search, with positional selection for lists. An idb accessibility dump is used where Appium under-reports the tree.

What if an element has no accessibility ID?

Text and container strategies are tried. If those fail, the step fails and the app developers must add a testID. There is no vision or OCR fallback.

Can multiple tests run at once?

Not within one run — there is no parallel execution. Multiple agents can each hold one job, so concurrency is bounded by agent count and available simulators.

AI

Where is AI actually used?

Three narrow places: suggesting how to clear an unexpected blocking screen during a run; planning which scenarios a PR should exercise; and drafting root-cause narratives after a failure. The LLM does not drive the test.

Is the AI autonomous?

No. It executes scenarios people wrote. Its runtime authority is limited to suggesting a control to tap when a screen blocks progress — and that suggestion is verified against a screen-change signature before being reported as successful, precisely because it has been wrong before.

Can AI generate tests?

Not in practice. An LLM test-generator class exists in ai/services/generator.py but no API endpoint or UI reaches it. It is unreachable code.

Can AI recover from failures?

No. A self-healing engine exists, but the only route to it is an endpoint the agent never calls — and even then it stores a suggestion for human review rather than retrying. No test has ever been healed automatically.

What if AI cannot identify an element?

The step fails with the ambiguity recorded, and the rest of the segment is skipped. It does not guess.

PR testing

Can we test every PR automatically?

Yes, via GitHub webhooks — subject to the webhook endpoint being reachable, which today means a tunnel such as ngrok.

Can results be sent back to GitHub?

Yes for webhook-triggered runs — a comment and a commit status. No for PR tests started from the dashboard, which carry a different trigger prefix and skip the write-back. Section 10 has the detail.

Is the PR build isolated from previous runs?

Yes. The worktree is reset before checkout and the app uninstalled before install, so a PR is tested rather than a leftover.

Infrastructure

What is required to run it?

A macOS machine with Xcode and simulators, Node.js with Appium and the XCUITest driver, idb, Python 3 with the project venv, and Git. macOS is mandatory — iOS simulators exist nowhere else.

Can it run in CI/CD?

A GitHub Actions workflow template exists and would require a self-hosted macOS runner. It is not installed in any repository today, and this repository has no .github/workflows directory.

Is it containerised?

No. No Dockerfile or compose file exists — and iOS simulators cannot run in Linux containers, so this is a platform constraint, not an oversight.

Security

How are GitHub tokens handled?

Read from environment variables via a .env file, which was untracked from Git with a sanitised .env.example left in place. Tokens are masked in log output by a redaction filter — which was repaired in revision 2 after it was found not to cover named child loggers.

How does the execution agent authenticate?

With a shared AGENT_TOKEN presented as an X-Agent-Token header and compared using a constant-time comparison. Before revision 2 the agent endpoints were unauthenticated.

Does it need access to source code?

Yes. It clones repositories and builds them, so it requires repository read access.

What application data does it store?

Run results, logs and screenshots of app screens. Screenshots of authenticated sessions may contain whatever test data was on screen. Test-account credentials for the business app are held in .env.

Scalability

Can multiple devices be used at once?

For build deployment, yes — one build fans out to every selected simulator. For test execution, a cross-app flow uses two simulators in sequence. Independent tests do not run in parallel.

Is there a job queue and are agents supported?

Yes to both. The queue is database rows with atomic claiming; agents register, heartbeat and poll. 46 agent registrations across 4 hostnames are recorded — though all currently show offline.

Can it scale horizontally?

Partly, and not yet proven. The pull-based agent model is the right shape for it, and additional Macs could run agents. But the backend is a single process over SQLite with in-memory run state, and orphan recovery only runs at startup. Horizontal scale needs those addressed first.

Section 17

Current Limitations

Platform and device

  • iOS simulators only. No physical device support of any kind.
  • macOS only. Xcode, simctl and idb are hard requirements.
  • Android unproven. Code exists; no Android project, no Android run.
  • Single host. Everything runs on one machine today.

Application-side dependencies

  • Accessibility identifiers are required for controls without stable text. No workaround exists platform-side.
  • Appium under-reports some React Native trees — one screen returned 4 elements where 75 existed. Mitigated by idb, not eliminated.
  • Some controls need pixel-offset tapping, which is device-geometry-specific and fragile.

Coverage

  • 34 scenarios total; by the team's own tracking a substantial part of the intended consumer catalogue is unwritten and much of what exists is unproven against the app.
  • 106 of 181 runs failed. Some are genuine defects, some infrastructure, some scenario bugs — the platform does not classify them automatically.
  • PR tests target a production app build with no test data at the pinned coordinates, so they cannot currently pass.

Execution and recovery

  • No test retry — a flaky failure is a failure.
  • Orphan recovery runs only at startup and only for cross-app bot types; a job orphaned while the backend stays up is never reclaimed.
  • Finalisation depends on in-memory state — a backend restart mid-run can lose the verdict.
  • No parallel execution within a run.
  • No Appium health-check-and-restart loop.

Features that exist but do not function

  • Visual regression — fully coded, zero results ever produced.
  • Self-healing — unreachable from the agent's execution path.
  • AI test generation — no endpoint or UI reaches it.
  • Slack alerts — no webhook URL configured.
  • Jira — credentials currently rejected; 1 ticket in the database.
  • CI/CD — a template, not an installed pipeline.

Reporting

  • No PDF export, no scheduled digest, no email.
  • RCA narratives cover 4 of 106 failures.
  • Specific UI defect classes — truncation, overlap, misalignment — are not detected as such.

Production readiness verdict

The two high-severity items and three medium ones are now fixed and verified against a running server. The platform no longer depends on network position for its authentication.

What remains before production exposure:

  • Set APP_ENV=production on the production host. Every fail-closed check keys off it, and it currently reads dev. This is the single most important deployment step — without it the guards stay in permissive mode.
  • Set GITHUB_WEBHOOK_SECRET to match the value configured on the GitHub webhook, or webhook delivery will 503 in production.
  • Role enforcement is still absent. Any authenticated user can delete projects and scenarios.
  • Move off SQLite if more than one backend process will ever run.
  • Rotate the GitHub and LLM tokens that were in the working tree before .env was untracked, and adopt a retention policy for run screenshots.
Deployment checklist

On the production host, before first start: APP_ENV=production, JWT_SECRET_KEY, AGENT_TOKEN (same value in the agent's environment), GITHUB_WEBHOOK_SECRET. The backend refuses to start without the signing key, which is the intended behaviour — a server that will not boot is safer than one signing tokens with a public constant.

Section 22

Client Presentation

What the platform is

It is an in-house test automation system for iOS applications, built specifically for a connected pair of restaurant apps — one for diners, one for staff. It takes test procedures a person would otherwise perform by hand on a phone and a tablet, and runs them unattended against iOS simulators.

Its distinguishing capability is testing a business transaction across applications. A diner books a table and pre-orders; a waiter opens that reservation and assigns a table; the kitchen receives that order and marks it ready. The platform runs all three roles as one test, on two devices, verifying that the same transaction genuinely propagates through the system rather than that each app works alone.

It is a working internal tool with real usage behind it — 181 recorded runs, 34 scenarios, 11 cross-app flows — running today on a single Mac. It is not a commercial product and not a hosted service.

What it currently does

  • Runs iOS UI tests written as plain-English steps on iOS simulators
  • Executes multi-app, multi-role journeys across two devices
  • Pulls source, builds an app, installs it, and confirms the version on the device
  • Deploys one build to several simulators at once
  • Discovers pull requests and tests a chosen PR branch on a chosen device
  • Queues runs and executes them through a polling agent
  • Records every run with per-step results, screenshots, logs and duration
  • Renders a screenshot-backed HTML report and pass/fail trends
  • Lets a QA engineer author tests by typing steps or by tapping a live simulator

What problems it solves

  • The manual effort of testing one transaction across two apps and three staff roles
  • Needing to write Appium code for every test case
  • Per-engineer Appium and simulator setup
  • Uncertainty about which build is on a device
  • Getting a test verdict on a code change before it merges
  • Test results living in one person's terminal

How it improves automation practice

  • Tests are data, not code — authored and edited in a browser
  • Element resolution is layered, so tests survive some UI change without editing
  • It refuses to guess. An ambiguous target fails the step rather than substituting something plausible
  • It verifies after acting. Screen changed, version installed, role correct — checked rather than assumed
  • A failed step aborts its segment, so later steps cannot produce a false verdict from the wrong screen

What makes it valuable

  • It automates the specific test people most dislike doing by hand
  • Non-programmers can author and maintain tests
  • Its green results are trustworthy, because it is engineered to fail loudly rather than pass optimistically
  • The evidence trail — screenshots, per-step detail, versions — makes failures discussable
  • Its architecture is the right shape for growth: a job queue and pull-based agents

Current limitations, stated plainly

  • iOS simulators only — no physical devices, and Android is unproven code
  • Requires a Mac with Xcode; cannot be containerised
  • Coverage is thin — 34 scenarios, much of the intended catalogue unwritten
  • No parallel execution, no test retry, and orphaned jobs are only reclaimed at backend startup
  • Visual regression, self-healing and AI test generation exist in code but have never functioned
  • PR results post to GitHub only for webhook-triggered runs
  • Role enforcement is absent — any authenticated user can delete projects and scenarios
  • Controls without accessibility identifiers cannot be automated until developers add them

What can be demonstrated today

  • A cross-app journey end to end — booking on the consumer app appearing on the waiter's screen and reaching the kitchen, on two simulators
  • Authoring a test by tapping — open the recorder, tap through a flow, save it as a scenario, run it
  • Editing a scenario in the browser and re-running it immediately
  • One-click deploy — pull, build, install to several simulators, with the version confirmed from each device
  • The queue in motion — a run moving from queued to running to a verdict, with live screen frames
  • A rich report from any of 181 historical runs, with per-step screenshots
  • Selecting a pull request and starting a test against its branch on a chosen device
  • A refusal to guess — a deliberately ambiguous step failing with its reason recorded, rather than silently doing the wrong thing

The honest one-sentence summary. A working iOS test automation platform with a genuinely distinctive cross-app capability and unusually disciplined verification, whose authentication has now been closed off properly, currently limited by scenario coverage rather than by its machinery.
